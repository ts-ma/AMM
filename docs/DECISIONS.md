## 3. Gate R = (b) — approved 2026-11-17

### Rules

- Surplus (`balance > reserve`) has exactly one destination: anyone may call `skim()`, which sends it to `surplusRecipient`.
- `sync()` stays public but **may only lower** recorded reserves (deficit reconciliation). It never absorbs surplus into reserves.
- Student intent: surplus goes to an official address, which may return it to mistaken senders off-chain or keep it as protocol income. Separate on-chain surplus accounting may be considered later (`FUTURE-ONLY`).

### Revision of v0.3

In v0.3, `sync()` could set reserves to actual balances, absorbing surplus. Under (b) it cannot, so the v0.3 first-mover race between `sync()` and `skim()` no longer exists.

### Trade-offs to disclose in the report

- The contract cannot identify who sent an unsolicited transfer and cannot force a refund. Refunds depend entirely on off-chain trust in whoever controls `surplusRecipient`.
- `surplusRecipient` has no privileged functions but is an economic beneficiary. Ownerless does not mean "no beneficiary".
- Surplus stays in the Pool until someone pays gas to call `skim()`.
- LPs never benefit from unsolicited transfers.
  - **M10 scope note (2026-11-23, wording only; Gate R unchanged).** The sentence holds for **surplus that has already formed** (`balance > reserve`): it never enters the reserves and leaves only through `skim()`. Two cases are outside it:
    - A direct transfer **while the token is in deficit** (`balance < reserve`) first refills the backing of the recorded reserve: up to the deficit it creates no surplus, and it spares the LPs the loss that `sync()` would book (it lifts the `ReserveDeficit` block once `balance ≥ reserve`, by the entry check's definition; derived from the code, not tested). Only the part above the reserve is surplus.
    - A depositor's **unmatched contribution** `u_i` inside `addLiquidity` (M8-2, X1) is not an unsolicited transfer: it enters the reserves, benefits all LP shares pro rata (the depositor's new shares included) and can move the price. It is bounded by the depositor's `maxExcess_i`.
  - **M10 disclosure (Gate R kept, student 2026-11-23).** For an unsupported positive-rebase or yield-bearing token, the growth of the Pool's balance is surplus and goes to `surplusRecipient` through `skim()`, not to the LPs.

### Rejected alternatives

- (a) Both public with surplus-absorbing `sync()`, accepting the race.
- (c) `sync()` performs a skim internally before reconciling. Equivalent to calling `skim()` then `sync()`, but a failing transfer of one token would block deficit reconciliation of the other.

### Why U10 affects the function signature

*Historical: U10 is superseded by M8-1 / M8-8 (§0.1). The principle stated here (fix the interface before implementing against it) was applied again to the M8-8 struct ABI.*

A Pool cannot query a token's transfer-tax rate on-chain, so the caller must supply it as a parameter. Parameters are part of the function signature, which determines the function selector. Adding the parameters in M8 after writing `addLiquidity` in M4 would change the public interface and every test calling it. Hence the interface is fixed before M4.

## 15. M8 decisions (approved 2026-11-21 to 2026-11-23; implemented and tested; M8 accepted 2026-11-23)

M8 is repositioned from a known-tax exact-gross algorithm (L-α) to a **tax-hint-independent, measured-net deposit**. The student's goal: a general-purpose AMM for real users. Unknown, random and dynamically changing taxes, tokens without a tax getter, and extra sender-side debits are compatibility goals where economically safe; safety, correct accounting, user protection and the ability to exit take priority over transaction success. Tax hints may exist in a UI for quotation only; the Pool must not need them for correct settlement.
